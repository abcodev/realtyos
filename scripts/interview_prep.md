## 1. 도입 · 경험 소개

---

**Q. Elasticsearch 써보신 경험 간단히 소개해주세요.**

부동산 실거래 검색 서비스에서 ES를 직접 설계하고 구축했습니다.
전국 수백만 건의 실거래 데이터를 대상으로 지역·가격·면적·연도 조건으로 검색하는 기능인데요,
Spring Data ES 같은 추상화 레이어 없이 RestClient로 HTTP를 직접 호출하는 방식을 선택했습니다.
이유는 ES 버전이나 OpenSearch로 교체할 때 클라이언트 라이브러리 의존성 없이 URL과 인증만 바꾸면 되고, 쿼리 DSL을 완전히 제어할 수 있어서입니다.
인덱스 매핑 설계, 색인 파이프라인 구축, 쿼리 최적화까지 전반을 담당했습니다.

---

**Q. 그 외에 검색이나 데이터 파이프라인 관련해서 해보신 게 있나요?**

같은 서비스에서 RAG(Retrieval-Augmented Generation) 파이프라인도 구축했습니다.
실거래 데이터를 텍스트 문서로 변환하고 임베딩해서 pgvector에 저장한 뒤,
사용자 자연어 질문을 벡터 검색으로 관련 거래를 찾고 LLM에 컨텍스트로 전달하는 구조입니다.
OpenAI와 로컬 Ollama를 모두 지원하고, 비용 절감을 위해 짧은 질문은 로컬 모델로 라우팅하는 설계도 포함했습니다.

## 2. ES 기본 원리

---

**Q. ES에서 문서를 색인하면 내부적으로 어떤 과정이 일어나나요?**

크게 세 단계입니다.

첫째, 문서가 들어오면 in-memory buffer에 쌓이고 동시에 Translog에 기록됩니다.
Translog는 장애 시 복구를 위한 WAL 역할을 해서, 버퍼가 날아가도 재시작 시 복구됩니다.

둘째, refresh가 일어나면(기본 1초) 버퍼가 새 Lucene 세그먼트로 변환되면서 검색 가능한 상태가 됩니다.
ES가 "Near Real-Time" 검색이라고 부르는 이유가 여기 있습니다.

셋째, flush가 일어나면(30분 또는 translog 크기 초과) Lucene commit이 실행되고 translog가 비워집니다.

문서 삭제나 업데이트는 기존 세그먼트를 수정하지 않고 .del 파일에 삭제 표시만 합니다.
실제 공간 회수는 세그먼트 merge 때 이루어집니다.

---

**Q. refresh_interval을 왜 조정하나요? 어떤 영향이 있나요?**

기본값 1초로 두면 색인할 때마다 세그먼트가 생성됩니다.
세그먼트가 많아지면 검색 시 모든 세그먼트를 순회해야 해서 검색이 느려지고, merge 부하도 늘어납니다.

대량 색인할 때는 30초나 -1(비활성화)로 설정해서 색인 throughput을 높이고,
색인이 끝나면 원래 값으로 돌려놓는 방식을 씁니다.

제가 구축한 서비스에서도 30초로 설정했는데,
5초마다 스케줄러가 소규모 배치로 색인하는 구조라 1초 refresh는 과도하고,
30초 지연도 실거래 검색 특성상 허용 가능했기 때문입니다.

---

**Q. 샤드를 어떻게 설계하셨나요? 샤드 수 결정 기준이 있나요?**

일반적인 기준으로는 샤드 하나의 크기를 10~50GB로 유지하고,
노드당 힙 1GB당 관리 샤드 수를 20개 이하로 잡는 것이 권장사항입니다.

제가 만든 서비스는 초기 단계라 데이터 규모가 크지 않아 샤드 1개, 레플리카 0개로 구성했습니다.

중요한 점은 primary 샤드 수는 인덱스 생성 후 변경이 불가능하다는 거라,
향후 데이터 증가를 감안해서 노드 배수로 설정하는 게 맞습니다.
예를 들어 노드 3대라면 샤드를 3의 배수로 설정해 균등 분산이 되도록요.

샤드 라우팅은 기본적으로 `hash(document_id) % 샤드수`로 결정되는데,
같은 지역 데이터를 같은 샤드에 모으려면 커스텀 라우팅을 쓸 수 있습니다.
지역 기반 검색이 많다면 이를 통해 검색 시 탐색 샤드 수를 줄일 수 있습니다.

## 3. 인덱스 설계

---

**Q. 매핑 설계할 때 어떤 부분을 중요하게 보셨나요?**

크게 세 가지를 봤습니다.

첫째, text와 keyword 구분입니다.
전문 검색이 필요한 필드는 text로, 정렬·집계·정확 매칭이 필요한 필드는 keyword로 분리했습니다.
아파트명처럼 둘 다 필요한 경우엔 text 타입에 keyword 서브필드를 두는 multi-field 방식을 썼습니다.

둘째, 숫자처럼 생긴 문자열 처리입니다.
실거래 금액이 "3,500" 같은 문자열로 오는데, range 필터는 숫자 타입이어야 합니다.
그래서 색인 시 파싱해서 원본 문자열 필드와 숫자 필드를 따로 저장했습니다.

셋째, dynamic mapping을 엄격하게 제어했습니다.
dynamic을 true로 두면 예상치 못한 필드가 들어올 때 타입 충돌이 생길 수 있어서,
명시적으로 매핑을 정의하고 정의되지 않은 필드는 에러가 나도록 했습니다.

---

**Q. 부분 검색은 어떻게 처리하셨나요?**

Nori와 ngram을 multi-field로 함께 사용했습니다.

`aptName` 기본 필드에는 Nori를 적용해 한국어 형태소와 복합어를 처리하고,
`aptName.ngram` 서브필드에는 min_gram 2, max_gram 30의 ngram을 적용했습니다.
"래미안대치팰리스"를 색인하면 "래미", "래미안", "래미안대", ... 이런 식으로 모든 부분 문자열이 토큰으로 저장됩니다.
그러면 "래미안"으로 검색해도 찾을 수 있고, "대치팰리스"로 검색해도 찾을 수 있습니다.

검색어는 Nori로 분석하고 `aptName^2`와 `aptName.ngram`을 함께 조회합니다.
Nori 필드에 더 높은 boost를 줘 의미 단위로 정확히 일치한 문서를 우선하고,
ngram 필드는 고유명사 오분석과 부분 문자열 검색을 보완하는 recall 채널로 사용했습니다.

트레이드오프로 Nori만 사용할 때보다 인덱스 크기와 색인 비용이 증가합니다.
min_gram을 낮게 잡을수록 토큰 수가 폭발적으로 늘어나기 때문에,
실제로는 검색 패턴을 분석해서 min_gram을 올리는 방향으로 최적화해야 합니다.

---

**Q. 인덱스 관리 전략으로 ILM 같은 거 써보셨나요?**

직접 운영해보진 않았지만 설계 관점에서는 이해하고 있습니다.

데이터를 Hot-Warm-Cold-Delete 단계로 관리하는 건데,
최신 데이터는 Hot tier에서 빠른 SSD로 제공하고,
오래된 데이터는 Warm에서 읽기 전용으로 압축해서 보관하는 방식입니다.

특허 데이터처럼 오래된 데이터도 검색해야 하는 경우엔
Cold tier에 두고 force merge로 세그먼트를 1개로 줄여서 디스크를 최소화하는 전략이 있고,
자주 쓰지 않는 인덱스는 frozen으로 두어 힙 사용을 최소화할 수도 있습니다.

이번 포지션에서 ILM 운영을 직접 경험하게 되면 빠르게 익힐 수 있을 것 같습니다.

## 4. 검색 쿼리 설계

---

**Q. bool 쿼리의 must, filter, should, must_not 차이가 뭔가요?**

핵심 차이는 스코어 계산 여부와 캐싱입니다.

must와 should는 query context여서 BM25 스코어를 계산합니다.
filter와 must_not은 filter context여서 스코어 계산을 건너뛰고, Lucene bitset으로 캐싱됩니다.

같은 filter 조건이 반복되면 캐시에서 바로 꺼내 쓸 수 있어서 성능이 올라갑니다.

실제로 제가 만든 실거래 검색에서는 지역·가격·면적·연도 조건이 모두 filter에만 있습니다.
실거래 검색은 관련도 순위가 필요 없고 최신 거래를 먼저 보여주면 돼서,
BM25 스코어 계산 자체를 생략하고 dealDate 내림차순 정렬만 씁니다.

반면 아파트명으로 연관도 순위가 필요한 검색이라면 must에 넣어야 합니다.

---

**Q. should 절을 filter 안에 쓸 때 주의할 점이 있나요?**

네, 흔한 실수 포인트입니다.

bool query 안에서 should의 minimum_should_match 기본값은 1이라 하나 이상 매칭해야 합니다.
그런데 filter 안에 should를 넣으면 기본값이 0이 돼서 아무 조건도 만족 안 해도 통과됩니다.

filter 안에서 OR 조건을 원한다면 minimum_should_match: 1을 명시해야 합니다.
아니면 filter 레벨에서 중첩 bool 쿼리를 쓰는 방식으로 해결할 수도 있습니다.

---

**Q. 검색 결과 점수를 커스텀하게 조정해야 했던 경험이 있나요?**

ES 쪽에서 직접은 아니지만, RAG 파이프라인에서 비슷한 문제를 다뤘습니다.

벡터 검색 결과에서 코사인 유사도만 쓰면 오래된 거래가 위에 올라오는 문제가 있었습니다.
그래서 유사도 점수에 최신성 점수를 결합하는 방식을 썼는데,
`final_score = similarity * 0.7 + recency_score * 0.3`
recency_score는 오늘 날짜에서 거래일 차이를 365일 기준으로 정규화한 값입니다.

ES에서 이와 동일한 걸 하려면 function_score 쿼리를 씁니다.
gauss 함수로 거래일이 최근일수록 높은 점수를 주고, boost_mode로 기존 점수와 곱하는 방식입니다.

---

**Q. wildcard 쿼리를 쓰면 안 된다고들 하는데, 왜 그런가요?**

wildcard나 regex 쿼리는 역색인의 이점을 활용하지 못합니다.
`*래미안*` 같은 앞뒤 와일드카드는 전체 역색인 항목을 순회해야 해서
데이터가 많아질수록 선형적으로 느려집니다.

대안은 색인 시점에 ngram으로 부분 문자열을 미리 만들어두고
검색은 일반 match 쿼리로 하는 겁니다.
저도 그 방식을 썼고, 훨씬 빠릅니다.

접두어 검색만 필요하다면 edge_ngram이 더 효율적입니다.
"래미"로 시작하는 단어만 찾는 경우에는 앞에서부터만 토큰을 만들어서 인덱스 크기를 크게 줄일 수 있습니다.

---

**Q. 대규모 쿼리 최적화를 해보신 경험이 있나요?**

쿼리 구조 최적화 측면에서 몇 가지 적용했습니다.

하나는 filter를 must보다 먼저 실행되도록 배치하는 겁니다.
bool 쿼리 실행 순서가 filter → must → should라서,
filter로 먼저 문서 수를 줄이면 BM25 계산 대상이 작아집니다.

둘은 응답에서 필요한 필드만 `_source` 로 지정하는 겁니다.
불필요한 필드를 가져오지 않으면 네트워크 전송량과 역직렬화 비용이 줄어듭니다.

셋은 집계 쿼리 최적화입니다.
keyword 필드 집계는 doc_values를 쓰는데, 이걸 fielddata로 text 필드에 켜면 힙을 많이 씁니다.
집계는 반드시 keyword 타입이나 numeric 타입에만 써야 합니다.

느린 쿼리를 찾으려면 slowlog 설정을 쓰고, explain API로 어느 절에서 비용이 큰지 분석할 수 있습니다.

## 5. 인덱싱 파이프라인 · 데이터 처리

---

**Q. 실시간으로 변하는 데이터를 ES에 색인할 때 어떻게 신뢰성을 확보하셨나요?**

Transactional Outbox 패턴을 썼습니다.

DB에 데이터를 저장할 때 같은 트랜잭션에서 outbox 테이블에도 "색인 대기" 상태를 기록합니다.
별도 스케줄러가 5초마다 outbox를 polling해서 ES에 bulk 색인하고,
성공하면 INDEXED, 실패하면 FAILED로 상태를 업데이트합니다.

실패 시엔 지수 백오프로 재시도합니다. 2^n초 간격으로 최대 300초까지 늘어나고,
5회 이상 실패하면 DEAD 상태로 두고 별도로 확인합니다.

이 방식의 장점은 ES가 잠깐 죽어도 데이터가 outbox에 남아 있어서 자동으로 복구된다는 겁니다.
ES 장애가 서비스 전체 장애로 번지지 않습니다.

Kafka를 쓰는 방법도 있는데, 초기 단계에서 브로커 운영 비용 없이 동일한 보장을 DB만으로 달성할 수 있어서 이 방식을 선택했습니다.

---

**Q. 대량 데이터를 한꺼번에 색인해야 한다면 어떻게 하시겠어요?**

Bulk API를 쓰되 몇 가지를 같이 세팅합니다.

색인 중에는 refresh_interval을 -1이나 30초로 올립니다. 1초마다 세그먼트가 새로 생기면 merge 부하가 쌓입니다.

replica를 0으로 내립니다. 색인 시 replica에 복제하는 비용이 없어져서 throughput이 2배 가까이 올라갑니다.
색인 완료 후 replica를 다시 1로 올리면 됩니다.

배치 크기는 한 요청당 5~15MB 정도가 적당하고, 너무 크면 ES 서버 GC 압박이 생깁니다.

색인 완료 후 force merge를 1 세그먼트로 줄이면 검색 성능도 좋아집니다.
단, force merge는 CPU·디스크 I/O를 많이 쓰니 트래픽이 적은 시간에 해야 합니다.

---

**Q. 대량 데이터를 ES에서 읽어올 때 Scroll과 Search After 차이가 뭔가요?**

Scroll은 스냅샷 기반입니다. 첫 요청 시점의 인덱스 상태를 고정해두고 페이지를 넘기는데,
scroll context가 힙을 점유합니다. 동시에 많은 scroll이 열려 있으면 OOM 위험이 있고,
ES 8에서는 deprecated 방향이라 새로 개발할 때는 쓰지 않는 게 좋습니다.

Search After는 cursor 방식입니다.
마지막 결과의 sort 값을 다음 요청에 넘기는 방식이라 힙 사용이 없고,
색인 중 새 데이터도 반영됩니다.

단점은 특정 페이지로 바로 점프가 안 된다는 거라서,
"5페이지 바로 보기" 같은 기능은 구현하기 어렵습니다.

제가 만든 재색인 기능도 동일한 원리를 씁니다.
마지막 처리한 ID를 기억해뒀다가 다음 배치에서 `WHERE id > lastId` 로 이어서 처리합니다.

---

**Q. bulk 색인 중 일부 문서만 실패하면 어떻게 처리하셨나요?**

ES bulk API는 일부 실패해도 전체 요청이 에러가 나지 않습니다.
응답 JSON에 errors 필드가 true이면 items 배열에서 실패한 항목만 가려낼 수 있습니다.

제가 구현한 코드에서는 errors가 true면 예외를 던져서 배치 전체를 재시도하는 방식을 썼는데,
이건 개선이 필요한 부분입니다.
실제로는 실패한 항목 ID만 뽑아서 그것만 재시도하는 게 더 효율적입니다.
성공한 99%는 멀쩡한데 1% 때문에 전체를 다시 색인하는 건 낭비이고,
ES에 불필요한 부하를 줍니다.

---

## 6. 운영 · 장애 대응

---

**Q. ES 클러스터가 yellow나 red가 됐을 때 어떻게 대응하시겠어요?**

먼저 상태를 확인합니다.
`GET /_cluster/health`로 전체 상태를 보고,
`GET /_cat/shards?v`로 어떤 샤드가 미배정인지, 이유가 뭔지 봅니다.
unassigned.reason이 NODE_LEFT면 노드 장애, ALLOCATION_FAILED면 설정 문제입니다.

yellow는 primary는 정상인데 replica가 미배정인 상태입니다.
서비스는 가능하지만 노드 하나가 더 죽으면 데이터 유실 위험이 있습니다.

red는 primary 샤드 자체가 미배정인 경우입니다.
해당 인덱스에 대한 색인과 검색이 불가능합니다.

대응은 원인별로 다릅니다.
노드 다운이라면 노드를 복구하는 게 먼저이고,
디스크가 차서 새 샤드를 못 배치하는 거라면 오래된 인덱스를 정리하거나 디스크를 추가합니다.
임시로 disk watermark 임계값을 올려서 숨통을 트이게 할 수 있지만 근본 해결은 아닙니다.

---

**Q. ES 힙 메모리는 어떻게 설정하시겠어요?**

두 가지 원칙이 있습니다.

첫째, 전체 RAM의 50%를 넘기지 않습니다.
나머지 50%는 OS page cache로 써야 합니다.
Lucene은 세그먼트 파일을 OS 파일 캐시에 올려놓고 쓰는데,
힙이 너무 크면 page cache 공간이 줄어 디스크 I/O가 증가합니다.

둘째, 32GB를 넘기지 않습니다.
JVM Compressed OOP가 32GB 이하에서만 적용되는데,
이게 깨지면 포인터 크기가 4바이트에서 8바이트로 커져서 메모리 효율이 급격히 떨어집니다.
RAM이 64GB 서버라면 힙은 31GB로 설정하는 게 최적입니다.

그리고 Xms와 Xmx를 같게 설정해야 합니다.
다르게 하면 GC가 일어날 때 힙 크기가 변동하면서 STW(Stop-The-World)가 길어집니다.

---

**Q. 검색 응답이 갑자기 느려졌다는 신고가 들어오면 어떻게 디버깅하시겠어요?**

단계별로 원인을 좁혀갑니다.

먼저 `GET /_cat/nodes?v`로 CPU, 힙 사용률, 디스크 I/O를 확인합니다.
특정 노드에 부하가 몰렸는지 전체적으로 높은지 봅니다.

다음으로 thread pool 상태를 봅니다.
`GET /_cat/thread_pool?v`에서 search queue나 rejected 수가 올라가 있으면 요청이 처리를 못 따라가는 겁니다.

GC 로그도 확인합니다.
GC STW가 길어지면 검색 응답 시간이 튑니다.
힙 사용률이 80% 이상이면 GC 원인일 가능성이 높습니다.

slowlog가 설정돼 있으면 느린 쿼리를 찾을 수 있습니다.
특정 쿼리 패턴이 문제라면 explain API로 어느 절에서 비용이 집중되는지 봅니다.

인덱스 레벨 문제라면 세그먼트 수가 너무 많은 건 아닌지 확인합니다.
세그먼트가 많으면 검색이 모든 세그먼트를 순회하면서 느려지는데, 이 경우 force merge로 줄일 수 있습니다.

---

**Q. ES를 운영하면서 가장 주의해야 할 안티패턴이 뭐라고 생각하세요?**

몇 가지가 있는데 실제로 설계하면서 의식했던 것들입니다.

하나는 Text 필드에 fielddata 켜는 겁니다.
Text 필드로 집계하려면 fielddata를 활성화해야 하는데, 이게 힙에 올라가서 OOM 원인이 됩니다.
집계가 필요한 필드는 반드시 keyword 서브필드나 keyword 타입으로 별도 관리해야 합니다.

둘은 무분별한 wildcard 쿼리입니다. 앞에서도 말씀드렸지만 전체 역색인 순회라 선형적으로 느립니다.

셋은 deep pagination입니다.
`from: 10000, size: 10` 같은 요청은 ES가 내부적으로 10010개를 전부 수집해서 상위 10개를 자릅니다.
깊은 페이지로 갈수록 비용이 선형 증가합니다. Search After로 대체해야 합니다.

넷은 너무 많은 필드 mapping입니다.
mapping explosion이라고 부르는데, dynamic mapping이 켜진 상태에서 필드가 수천 개 이상 생기면 클러스터 메타데이터가 비대해져서 마스터 노드에 부하가 쌓입니다.

---

## 7. ES8 · OpenSearch 마이그레이션

---

**Q. ES8과 OpenSearch의 차이를 아시나요?**

OpenSearch는 Elastic이 2021년 라이선스를 변경하자 AWS 주도로 ES 7.10.2를 포크해서 만든 프로젝트입니다.

기술적 차이 중 제일 중요한 건 라이선스입니다.
ES는 Elastic License 2.0으로 SaaS 형태로 제공하는 건 제한이 있고,
OpenSearch는 Apache 2.0이라 자유롭게 상업 이용이 가능합니다.

API 레벨에서는 7.x 이후 점점 달라지고 있습니다.
OpenSearch는 7.x 호환을 유지하면서 자체 발전하고 있고,
ES 8은 k-NN, ELSER(Elastic Learned Sparse Encoder) 같은 자체 ML 기능을 추가했습니다.
클라이언트도 ES 공식 클라이언트와 OpenSearch 클라이언트가 별도로 있어서 교체가 필요합니다.

보안 설정도 다릅니다.
ES 8은 기본적으로 TLS와 X-Pack 인증이 켜져 있고,
OpenSearch는 Security 플러그인이 내장되어 있지만 비활성화도 가능합니다.

---

**Q. 다운타임 없이 ES에서 OpenSearch로 이전한다면 어떤 전략을 쓰시겠어요?**

Dual-Write 전략을 쓰겠습니다.

1단계에서 OpenSearch 클러스터를 구성하고 인덱스 매핑을 동일하게 만듭니다.

2단계에서 애플리케이션을 ES와 OpenSearch에 동시에 쓰도록 변경합니다.
이 시점부터 새 데이터는 양쪽에 다 들어갑니다.

3단계에서 과거 데이터를 OpenSearch로 복제합니다.
reindex API로 원격 ES에서 OpenSearch로 직접 당겨오거나,
ES의 snapshot을 OpenSearch에서 restore하는 방법이 있습니다.
ES 7.x 기반 스냅샷은 OpenSearch에서 복원이 가능합니다.

4단계에서 읽기 트래픽을 점진적으로 전환합니다.
10% → 30% → 50% → 100% 순으로 늘리면서 검색 품질과 응답 시간을 비교합니다.

5단계에서 검증이 끝나면 ES 쪽 write를 제거하고 클러스터를 해제합니다.

제가 구현한 Outbox 기반 색인 파이프라인은 이 전략에서 유리합니다.
reindex 시작 시점 이후의 신규 데이터가 outbox에 쌓이기 때문에,
reindex 완료 후 outbox가 자동으로 gap을 메워줍니다.

---

**Q. 마이그레이션 후 데이터가 제대로 이전됐는지 어떻게 검증하시겠어요?**

여러 레벨에서 검증합니다.

기본적으로 문서 수를 비교합니다. count API로 ES와 OpenSearch의 문서 수가 일치하는지 확인합니다.

그 다음으로 샘플 문서를 비교합니다.
랜덤으로 수백~수천 건 ID를 뽑아서 양쪽 _source가 동일한지 확인합니다.

가장 중요한 건 실제 검색 결과 비교입니다.
운영에서 자주 쓰는 주요 쿼리 패턴을 모아서 두 시스템에 동일하게 날려보고
결과 순서와 내용이 일치하는지 확인합니다.

분석기가 다르면 토크나이징 결과가 달라질 수 있어서,
중요한 필드에 대해 `/_analyze` API로 양쪽의 분석 결과도 비교해야 합니다.

---

## 8. 한국어 형태소 분석기

---

**Q. 한국어 검색 구현할 때 어떤 분석기를 쓰셨나요? 왜 그걸 선택하셨나요?**

부동산 서비스는 한국어 검색이 핵심이라 Nori와 ngram을 multi-field로 함께 사용했습니다.
ES 공식 플러그인이라 버전 호환성이 가장 안정적이고, mecab-ko-dic 기반이라 형태소 정확도도 높습니다.

기본 `aptName` 필드는 Nori의 `decompound_mode=mixed`를 사용해 복합어 원형과 분해 토큰을 함께 보존하고,
`nori_readingform`으로 한자 표기도 보완했습니다.

다만 "래미안대치팰리스" 같은 아파트 고유명사는 사전에 없으면 Nori가 엉뚱하게 분리할 수 있습니다.
그래서 `aptName.ngram` 서브필드를 추가해 부분 문자열 검색과 미등록 고유명사를 보완했습니다.
검색할 때는 Nori 필드에 boost를 주고 ngram 필드를 함께 조회해 precision과 recall의 균형을 맞췄습니다.

---

**Q. Nori 분석기 구성 요소에 대해 설명해주세요.**

세 가지 핵심 구성요소가 있습니다.

nori_tokenizer가 핵심입니다. 형태소 단위로 텍스트를 분리하고, 복합어 처리 방식을 decompound_mode로 설정합니다.
`none`은 복합어를 쪼개지 않고, `discard`는 복합어를 쪼개면서 원형을 버립니다.
`mixed`는 원형과 분리된 형태소를 모두 색인합니다.

특허 도메인처럼 "리튬이온배터리"를 통째로도 찾고 "리튬", "배터리"로도 찾아야 한다면 mixed가 적합합니다.

nori_part_of_speech는 불필요한 품사를 제거합니다. 조사, 어미 등이 대상인데,
도메인에 따라 제거하면 안 되는 품사도 있어서 stoptags를 조정해야 합니다.

nori_readingform은 한자를 한글로 변환합니다. 특허 문서에 한자가 많다면 유용합니다.

---

**Q. 형태소 사전은 어떻게 운영하시겠어요?**

실제로 장기간 운영해본 경험은 없어서 솔직히 말씀드리겠습니다.
다만 운영 방법은 이해하고 있습니다.

Nori의 사용자 사전은 `userdict_ko.txt` 파일로 관리합니다.
"나노구조체 NNG" 형식으로 단어와 품사를 지정합니다.

신조어나 도메인 용어가 오분류되는 걸 탐지하는 건 주로 두 가지 방법입니다.
하나는 검색 결과 0건인 쿼리를 로그에서 수집하는 겁니다. 자주 쓰는 용어인데 결과가 없다면 오분류 신호입니다.
다른 하나는 `/_analyze` API로 특정 단어의 분석 결과를 직접 확인하는 겁니다.

사전을 업데이트하면 인덱스를 close했다가 open해야 새 사전이 적용됩니다.
그리고 이미 색인된 문서들은 구버전 토큰으로 남아있기 때문에,
중요한 변경이라면 전체 재색인도 함께 해야 합니다.

이 부분은 입사 후 기존 사전과 운영 프로세스를 빠르게 익히고 싶습니다.

---

**Q. 한국어 검색에서 자주 발생하는 품질 문제가 뭐가 있나요?**

몇 가지 전형적인 문제가 있습니다.

첫째, 복합어 처리입니다. "스마트폰배터리"를 검색하는데 색인에 "스마트폰"과 "배터리"가 따로 있거나,
반대로 "리튬이온배터리"가 엉뚱하게 분리되어 색인되는 경우입니다.

둘째, 동음이의어와 동형이의어입니다. "배"가 과일 배인지 선박 배인지 문맥에 따라 다릅니다.
형태소 분석기만으로는 해결 어렵고 문맥 임베딩 모델이나 필드 구분이 필요합니다.

셋째, 띄어쓰기 오류입니다. "삼성전자" vs "삼성 전자"를 동일하게 처리하려면
shingle 필터나 ngram으로 보완해야 합니다.

넷째, 브랜드명이나 고유명사가 사전에 없어서 쪼개지는 경우입니다.
신규 브랜드명이나 특허 기술 용어가 계속 생기기 때문에 사전 관리가 중요합니다.

---

## 9. Vector Search · RAG

---

**Q. Vector Search가 기존 키워드 검색과 어떻게 다른가요?**

키워드 검색은 정확한 단어 일치 기반입니다.
"전기차 배터리"로 검색하면 그 단어가 있는 문서만 찾습니다.
"EV 충전"으로는 못 찾습니다.

벡터 검색은 의미 기반입니다.
텍스트를 임베딩 모델로 고차원 벡터로 변환하고, 의미적으로 유사한 벡터 간의 거리로 검색합니다.
"전기차 배터리"와 "EV 충전"은 의미가 유사하니 가까운 벡터가 됩니다.

장단점이 명확합니다.
벡터 검색은 표현이 달라도 의미가 같으면 찾을 수 있지만,
"A61K 31/4709" 같은 정확한 코드 검색이나 날짜·가격 범위 필터는 약합니다.
그래서 특허 검색처럼 정확도와 의미 유사도가 둘 다 필요한 도메인에서는
Hybrid Search, 즉 키워드 검색과 벡터 검색을 결합하는 방식이 효과적입니다.

---

**Q. RAG를 구현하셨다고 하셨는데, 구체적으로 어떻게 설계하셨나요?**

크게 인덱싱 파이프라인과 검색·답변 파이프라인으로 나뉩니다.

인덱싱 쪽에서는 실거래 DB 레코드를 그냥 저장하지 않고 검색에 유리한 텍스트 포맷으로 가공했습니다.
"문서유형: 아파트 실거래가, 검색키워드: 실거래가 아파트 매매..." 같은 방식으로 도메인 키워드를 명시적으로 심어서,
임베딩 모델이 관련 개념에 가중치를 두도록 유도했습니다.

content_hash로 변경 감지를 해서 내용이 바뀐 문서만 재임베딩합니다.
바뀌지 않은 문서를 매번 임베딩하면 API 비용이 낭비되니까요.

검색·답변 쪽에서는 사용자 질문을 먼저 의도 분류합니다.
"A동이랑 B동 비교해줘"처럼 비교 의도면 LLM 없이 바로 정형 비교표를 만들고,
일반 검색이면 벡터 검색으로 관련 거래를 찾은 뒤 LLM에 컨텍스트로 전달합니다.

의도 분류를 LLM으로 하지 않고 규칙 기반으로 한 이유는 비용과 지연 때문입니다.
부동산 도메인 질문 패턴이 제한적이라 정규식과 키워드로 충분히 분류가 됩니다.

Hallucination 방지를 위해 근거 문서가 없으면 LLM 자체를 호출하지 않고,
LLM이 만들어낸 답변에서 근거 없는 내용이 감지되면 직접 만든 요약으로 대체합니다.

---

**Q. pgvector와 ES의 k-NN 중 왜 pgvector를 선택하셨나요?**

당시 판단 기준으로는 세 가지였습니다.

첫째, 인프라 단순성입니다. 이미 PostgreSQL을 쓰고 있어서 별도 시스템 없이 pgvector로 바로 도입이 가능했습니다.

둘째, 데이터 일관성입니다. 실거래 데이터가 PostgreSQL에 있고, 벡터도 같은 DB에 있으면 JOIN으로 한 번에 처리됩니다.
별도 벡터 DB를 쓰면 데이터 동기화 문제가 생깁니다.

셋째, 메타데이터 필터입니다. pgvector는 일반 SQL WHERE 조건과 벡터 검색을 같이 쓸 수 있어서
"강남구이면서 거래금액 5억 이상인 거래 중 유사한 것"을 단일 쿼리로 처리합니다.

단점은 수천만 건 이상에서 HNSW 인덱스 없이 쓰면 선형 탐색이라는 점입니다.
pgvector도 HNSW 인덱스를 지원하지만, 그 규모가 되면 ES k-NN이나 전용 벡터 DB를 검토해야 합니다.

특허 검색처럼 키워드 정확도와 의미 유사도가 둘 다 중요한 도메인이라면
ES의 Hybrid Search(BM25 + kNN을 RRF로 결합)가 훨씬 자연스러운 선택이라고 생각합니다.

---

**Q. Hybrid Search를 ES에서 구현한다면 어떻게 하겠습니까?**

ES 8에서는 RRF(Reciprocal Rank Fusion) retriever를 씁니다.

BM25 키워드 검색 결과와 k-NN 벡터 검색 결과를 각각 순위 목록으로 만들고,
각 문서의 순위를 `1 / (rank_constant + rank)` 로 변환해서 합산하는 방식입니다.
두 검색의 스코어 스케일이 달라도 순위만 가지고 결합하기 때문에 정규화 없이 안전하게 합칠 수 있습니다.

```json
"retriever": {
  "rrf": {
    "retrievers": [
      { "standard": { "query": { "match": { "content": "리튬이온배터리" } } } },
      { "knn":      { "field": "embedding", "query_vector": [...], "num_candidates": 100 } }
    ],
    "rank_constant": 60
  }
}
```

rank_constant 60이 기본값인데, 이 값이 클수록 순위 차이의 영향이 줄어듭니다.
최적 값은 도메인 특성에 맞게 벤치마크로 찾아야 합니다.

---

## 10. 특허 검색식 파서

---

**Q. 특허 검색식 파서를 개발한다면 어떻게 접근하시겠어요?**

특허 검색식은 불리언 연산자(AND/OR/NOT)와 근접 검색(W/N, ADJ), 필드 지정(TI:, AB:), IPC 코드가 섞인 복잡한 표현식입니다.

설계를 세 단계로 나눕니다.

첫째, Lexer입니다. 입력 문자열을 토큰 스트림으로 변환합니다.
AND, OR, NOT, W/5, ADJ, 괄호, 필드명, 검색어 토큰을 구분합니다.
ㅇ
둘째, Parser입니다. 토큰 스트림을 AST(Abstract Syntax Tree)로 변환합니다.
연산자 우선순위가 NOT > AND > OR이라서 이를 반영해야 합니다.
구현 방법으로는 ANTLR4로 문법을 정의하면 코드 자동 생성이 돼서 유지보수가 쉽고,
직접 구현한다면 Pratt Parser가 연산자 우선순위 표현에 적합합니다.

셋째, ES 쿼리 변환입니다. AST를 순회하면서 노드 타입에 맞게 변환합니다.
AND → bool.must, OR → bool.should, NOT → bool.must_not, 근접 검색 → span_near 쿼리입니다.

IPC/CPC 코드처럼 계층 구조가 있는 경우엔 prefix 쿼리나 계층을 미리 분해해서 저장해두는 방법을 씁니다.

---

**Q. 근접 검색(W/N 연산자)을 ES에서 어떻게 표현하나요?**

ES의 span_near 쿼리를 씁니다.

```json
{
  "span_near": {
    "clauses": [
      { "span_term": { "content": "리튬" } },
      { "span_term": { "content": "배터리" } }
    ],
    "slop": 5,
    "in_order": false
  }
}
```

slop이 최대 거리이고, in_order가 false면 순서 상관없이 5단어 이내에 있으면 매칭됩니다.
ADJ(바로 인접)는 slop 0에 in_order true로 표현합니다.

span 쿼리가 제대로 동작하려면 색인 시 term_vector에 위치 정보를 저장해야 합니다.
`"term_vector": "with_positions_offsets"` 설정이 필요합니다.
highlight 기능도 term_vector가 있어야 정확하게 동작합니다.

## 11. 성능 최적화 · 트레이드오프

---

**Q. 검색 파라미터를 최적화한 경험이 있나요? 어떤 지표를 보셨나요?**

ES 직접 파라미터 최적화보다는 RAG 검색 품질 최적화를 해봤습니다.

벡터 검색에서 topK를 몇으로 잡느냐에 따라 결과 품질과 응답 시간이 달라졌습니다.
너무 작으면 관련 문서를 놓치고, 너무 크면 LLM 컨텍스트 길이를 초과하거나 latency가 올라갑니다.
최종 결과 8건으로 제한하되, 검색은 20건까지 가져와서 조건 필터링 후 LLM에 전달하는 방식으로 정했습니다.

최신성 가중치도 0.3으로 설정했는데, 이 값은 "최근 거래가 검색 결과에서 올라오는가"를 실제 질문으로 확인하면서 조정했습니다.
데이터 기반 A/B 테스트보다는 도메인 지식 기반으로 초기값을 잡고, 이후 검색 로그로 검증하는 방식입니다.

ES 파라미터 최적화는 BM25의 k1, b 조정이나 ngram min/max gram 조정 같은 게 있는데,
이건 실제 검색 로그와 nDCG, MRR 같은 지표로 벤치마크해야 제대로 할 수 있습니다.
입사 후에 그 방식으로 체계적으로 해보고 싶습니다.

---

**Q. 레거시 시스템을 리팩토링해서 성능을 개선한 경험이 있나요?**

큰 규모의 레거시 리팩토링보다는 설계 단계에서 미래 교체를 염두에 두고 만든 경험이 있습니다.

ES 클라이언트를 직접 노출하지 않고 도메인 인터페이스(DealsSearchIndexer, DealsSearchQueryRepository)로 추상화했습니다.
덕분에 구현체는 ES인데, 나중에 OpenSearch나 다른 검색 엔진으로 바꿀 때 인터페이스만 유지하고 구현체만 교체하면 됩니다.
도메인 레이어나 서비스 레이어는 건드릴 필요가 없습니다.

또 색인 파이프라인도 Outbox 패턴으로 ES 의존성을 분리했습니다.
색인 실패가 서비스 장애로 번지지 않고, 나중에 Kafka 기반으로 교체하더라도 outbox queue 인터페이스만 바꾸면 됩니다.

레거시 시스템을 대규모로 리팩토링한 경험은 부족하지만,
이런 설계 원칙을 알고 있어서 레거시 분석 → 인터페이스 추출 → 점진적 교체 방식으로 접근할 수 있습니다.

---

**Q. 완벽한 설계보다 빠른 실험을 선호한다고 하셨는데, 본인은 어떤 편인가요?**

저는 빠른 가설 검증을 선호하는 편입니다.

RAG 파이프라인 구현할 때 처음에 의도 분류를 LLM으로 해야 하는지 규칙 기반으로 해도 되는지 불확실했습니다.
LLM 방식을 설계하는 데 시간을 쓰기보다, 규칙 기반으로 빠르게 만들어서 실제 질문 패턴에서 어느 정도 커버되는지 먼저 확인했습니다.
결과적으로 부동산 도메인에서는 규칙 기반으로 충분히 분류가 돼서 LLM 호출 비용 없이 처리할 수 있었습니다.

반면 완벽하게 설계하고 시작한다는 접근도 경우에 따라 필요하다고 생각합니다.
특히 인덱스 매핑은 primary 샤드 수처럼 나중에 바꾸기 어려운 결정이 있어서,
이런 부분은 충분히 고민하고 결정해야 합니다.

빠른 실험이 유효한 영역과 신중한 설계가 필요한 영역을 구분하는 게 중요하다고 생각합니다.

## 12. 추가 심화 질문

---

**Q. text와 keyword 타입의 차이를 설명해주세요.**

`text`는 analyzer를 거쳐 토큰 단위로 역색인되며 BM25 기반의 전문 검색에 사용합니다.
`keyword`는 전체 값을 하나의 토큰으로 저장해서 정확 일치, 필터, 정렬, 집계에 사용합니다.

아파트명은 검색과 정확 일치가 모두 필요하기 때문에 `aptName`은 text로 두고
`aptName.keyword` 서브필드를 추가하는 multi-field 방식으로 설계했습니다.
가격이나 면적은 문자열 원본과 별개로 숫자 필드를 만들어 range query가 가능하게 했습니다.

---

**Q. Analyzer, Tokenizer, Token Filter의 차이를 설명해주세요.**

Analyzer는 문자열을 토큰으로 변환하는 전체 파이프라인이고,
Character Filter, Tokenizer, Token Filter 순서로 동작합니다.

Character Filter는 HTML 제거나 문자 치환처럼 토큰화 전 원문을 정리합니다.
Tokenizer는 문장을 토큰으로 분리하고, Token Filter는 소문자화, 불용어 제거,
동의어 확장, 품사 제거처럼 생성된 토큰을 가공합니다.

현재 아파트명 기본 필드에는 `nori_tokenizer`와 `nori_readingform`을 적용했고,
부분 검색용 서브필드에는 ngram tokenizer를 적용했습니다.

---

**Q. Replica는 어떤 기준으로 설정하나요?**

Replica는 고가용성과 검색 처리량을 높이지만 디스크 사용량과 색인 비용도 증가시킵니다.
현재 저사양 단일 노드 환경에서는 replica를 배치할 다른 노드가 없기 때문에 0으로 설정했습니다.
여기서 replica를 1로 두면 replica shard가 unassigned되어 cluster health가 yellow가 됩니다.

소규모 고가용성 운영 환경으로 확장한다면 서로 다른 장애 도메인에 데이터 노드를 배치하고
replica를 최소 1개로 설정하겠습니다. Replica는 삭제와 손상도 복제하므로 백업을 대신하지 않으며,
별도의 snapshot과 PostgreSQL 원본 기반 재색인 절차가 필요합니다.

---

**Q. Alias를 이용한 무중단 재색인 절차를 설명해주세요.**

먼저 버전이 포함된 새 인덱스, 예를 들어 `real_estate_deals_v2`를 새 매핑으로 생성합니다.
기존 인덱스 데이터를 `_reindex`하거나 PostgreSQL 원본에서 다시 색인하고,
문서 수, 샘플 문서, 주요 검색 결과, analyzer 결과와 성능을 비교합니다.

검증이 끝나면 한 번의 `_aliases` 요청으로 읽기 alias를 기존 인덱스에서 새 인덱스로 원자적으로 전환합니다.
실시간 변경이 계속되는 환경이면 dual write나 변경분 재처리로 전환 직전의 데이터 차이도 제거해야 합니다.
문제가 생기면 alias를 이전 인덱스로 되돌리고, 안정화 이후 구 인덱스를 삭제합니다.

---

**Q. ES 7에서 ES 8로 이전할 때 무엇을 확인해야 하나요?**

먼저 Upgrade Assistant와 deprecation log로 제거 예정 API와 설정을 찾고,
플러그인, Java 클라이언트, 매핑, analyzer, index template의 호환성을 확인합니다.
ES 8에서는 보안 기능이 기본 활성화되고 transport와 HTTP 계층의 인증·TLS 구성이 중요해졌습니다.

운영 클러스터를 바로 올리기보다 동일 데이터의 테스트 클러스터에서 snapshot 복구 또는 재색인을 수행하고,
대표 쿼리의 결과 순위와 P95·P99 지연시간을 비교합니다.
롤링 업그레이드 가능 여부와 지원되는 버전 경로를 확인하고 반드시 rollback 절차를 준비합니다.

---

**Q. Deep Pagination 문제는 무엇이고 어떻게 해결하나요?**

`from=100000&size=20` 요청은 각 shard가 상위 100,020개 결과를 coordinator에 보내야 하므로
CPU와 heap 사용량이 커지고 shard 수가 많을수록 비용이 증가합니다.

사용자 화면의 연속 페이지 탐색에는 PIT와 `search_after`를 사용합니다.
정렬값이 같은 문서의 순서를 안정적으로 유지하려면 고유 ID 같은 tie-breaker를 정렬 조건에 추가합니다.
대량 추출 작업은 사용자 검색 API와 분리하고 상황에 따라 Scroll 또는 별도 배치 파이프라인을 사용합니다.

---

**Q. Object와 Nested 타입의 차이는 무엇인가요?**

일반 object 배열은 내부적으로 필드가 평탄화되므로 배열 원소 간 관계가 보존되지 않습니다.
예를 들어 발명자 이름과 국가 배열에서 서로 다른 사람의 값이 한 조건으로 잘못 결합될 수 있습니다.

`nested`는 각 배열 원소를 숨겨진 별도 Lucene 문서로 저장해 원소 단위 관계를 유지합니다.
정확성은 높지만 문서 수와 nested query 비용이 증가하므로,
배열 원소 간 결합 조건이 반드시 필요할 때만 사용해야 합니다.

---

**Q. BM25를 설명해주세요.**

BM25는 검색어가 문서에 얼마나 중요하게 등장하는지를 계산하는 기본 관련도 알고리즘입니다.
TF는 검색어가 문서에 등장한 빈도, IDF는 전체 문서에서 희귀한 단어에 주는 가중치,
문서 길이 정규화는 긴 문서가 단순히 단어를 많이 포함해서 유리해지는 문제를 보정합니다.

`k1`은 term frequency 증가가 포화되는 정도를, `b`는 문서 길이 보정 강도를 조절합니다.
감으로 값을 바꾸기보다 대표 질의와 정답 문서로 구성한 평가셋에서 MRR이나 NDCG를 비교해야 합니다.

---

**Q. 검색 품질은 어떻게 평가하나요?**

오프라인에서는 대표 질의마다 관련 문서를 라벨링한 평가셋을 만들고
Precision@K, Recall@K, MRR, NDCG를 측정합니다.
검색 결과가 없는 질의, 고유명사, 오타, 복합어처럼 실패하기 쉬운 질의를 별도 그룹으로 관리합니다.

온라인에서는 zero-result rate, reformulation rate, CTR, 전환율, 이탈률을 봅니다.
분석기, 사전, boost를 변경할 때는 기존 시스템과 결과를 비교하고 일부 트래픽에만 적용한 뒤
품질뿐 아니라 P95 지연시간, 오류율과 인덱스 크기도 함께 판단합니다.

---

**Q. Indexing 속도가 느려지면 어떻게 분석하나요?**

먼저 입력 생산 속도와 ES 처리 속도를 분리하고, Bulk 응답의 item별 오류와 처리시간을 확인합니다.
그다음 write thread pool queue와 rejection, CPU, heap/GC, disk I/O, merge와 refresh 부하를 봅니다.

매 요청 refresh, 지나치게 작은 Bulk, 과도한 replica와 ngram 토큰,
동적 매핑 폭증이 흔한 원인입니다. 병목에 따라 Bulk 크기 조정, refresh interval 증가,
불필요한 필드와 분석기 제거, producer backpressure를 적용하고 동일 데이터로 다시 측정합니다.

---

**Q. Embedding 모델을 교체하면 어떻게 이전하나요?**

모델이 바뀌면 벡터 차원뿐 아니라 의미 공간 자체가 달라지므로 기존 벡터와 새 벡터를 혼용하면 안 됩니다.
새 모델용 인덱스나 벡터 컬럼을 별도로 만들고 전체 문서를 다시 임베딩합니다.

동일 평가셋으로 Recall@K, MRR, 답변 근거성, 지연시간과 비용을 비교한 뒤 일부 트래픽으로 검증합니다.
문제가 없을 때 alias나 모델 버전 설정을 전환하고, rollback 기간 동안 기존 벡터를 유지합니다.

---

**Q. 특허 데이터는 어떻게 가공하고 인덱싱하겠습니까?**

서지정보, 제목, 초록, 청구항, 상세 설명, 발명자, 출원인, IPC·CPC를 구분해 매핑합니다.
특허번호와 분류코드는 keyword, 제목과 본문은 text, 출원일은 date로 저장합니다.
제목·초록·청구항에는 서로 다른 boost를 주고, 다국어 원문과 정규화 필드를 분리합니다.

RAG용으로는 문서 전체를 한 벡터로 만들지 않고 초록과 청구항을 의미 단위로 chunking합니다.
각 chunk에 특허번호, 청구항 번호, 출원일과 분류코드를 메타데이터로 저장해
키워드 필터와 vector search를 함께 사용할 수 있게 합니다.

---

**Q. 검색식 파서는 어떻게 테스트하나요?**

Lexer의 토큰화, parser의 AST 생성, AST에서 ES DSL로 변환하는 단계를 독립적으로 단위 테스트합니다.
연산자 우선순위, 중첩 괄호, quote와 escape, 필드 범위, NOT, 근접 검색을 포함해야 합니다.

빈 괄호, 닫히지 않은 따옴표, 잘못된 필드명, 지나치게 깊은 중첩 같은 실패 입력도 검증하고,
AST 깊이와 clause 수에 제한을 둬 악성 검색식이 클러스터 장애로 이어지지 않게 합니다.
마지막으로 실제 인덱스에 fixture 문서를 넣어 기대 문서가 검색되는지 통합 테스트합니다.
