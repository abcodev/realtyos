## 단계별 의사결정

### 1. RAG 검색 기반 만들기

초기 작업은 실거래 데이터를 RAG 문서로 만들고, 임베딩을 쌓고, 질문과 가까운 문서를 검색하는 구조를 만드는 데 집중했다.

핵심 작업:

- 실거래 데이터를 RAG 문서로 변환
- Ollama 기반 임베딩/답변 생성 연결
- 지역, 가격, 면적, 기간 조건을 검색 조건으로 반영
- 검색 결과를 유사도만 보지 않고 최신성과 함께 점수화

### 2. Query Rewrite 도입

사용자 질문은 대부분 자연어이므로, 검색 전에 구조화 조건으로 바꾸는 단계가 필요했다.

예시:

- `강남 30평대 아파트 시세`
- `서울 4억 미만 34.44㎡ 이상`
- `대치동과 잠실 20평대 비교`

이 단계에서 `RagQueryRewritePolicy`가 추가됐고, 지역/가격/면적/기간 조건 추출 테스트가 들어갔다.

### 3. 임베딩 적재 성능과 provider 선택

초기에는 임베딩 저장이 개별 insert 중심이어서 대량 데이터에 불리했다. 이후 batch insert로 변경하고, OpenAI/Ollama provider와 model을 선택할 수 있게 확장했다.

핵심 작업:

- `RagEmbeddingToSave` 도입
- batch insert 기반 임베딩 저장
- Ollama embedding batch size 설정화
- OpenAI/Ollama 임베딩 클라이언트 선택 구조 정리
- 실제 적재 테스트 흐름 추가

### 4. 사용자 AI 메모리

로그인 사용자의 최근 질문과 선호 조건을 기억해서 다음 질문에 반영하는 구조를 추가했다.

핵심 작업:

- `user_ai_memory`
- `user_ai_memory_event`
- 최근 질문 이벤트 저장
- 자주 묻는 지역 집계
- 메모리 조회/수정/삭제 API
- RAG 프롬프트에 사용자 맥락 주입

### 5. SSE 스트리밍

답변 생성 시간이 길어지면서 사용자 화면에서 응답이 멈춘 것처럼 보이는 문제가 있었다. 이를 해결하기 위해 SSE 기반 스트리밍 API를 추가했다.

핵심 작업:

- `/api/v1/rag/ask/stream`
- `RagAnswerStreamingService`
- `RagStreamEvent`
- Ollama streaming 호출
- 검색 진행, 모델 선택, token, completed 이벤트 분리

### 6. 로그인/OAuth2

사용자 기반 메모리와 히스토리 기능을 쓰기 위해 로그인 흐름이 추가됐다.

핵심 작업:

- 사용자 도메인 추가
- JWT 기반 인증 흐름
- Kakao/Google OAuth2 로그인
- OAuth redirect/callback 처리
- refresh token 재발급 흐름

### 7. 답변 품질과 guardrail

RAG 검색 결과가 엉뚱한 지역/문서를 가져오거나, 근거가 부족한데 답을 생성하는 문제가 있었다.

핵심 작업:

- `RagAnswerGuardrail`
- 조건과 근거가 맞는지 검사
- 근거가 부족하면 답변 생성 제한
- 실거래 근거 요약 답변 보강
- 비교 질문에서 지역별 검색 결과를 병합

### 8. 의사결정 엔진

단순 RAG 답변만으로는 “어디가 더 좋은지”, “갈아타기 후보”, “시세 비교” 같은 질문에 약했다. 그래서 실거래 DB를 직접 집계하는 deterministic 분석 엔진을 추가했다.

핵심 작업:

- `DealAnalysisService`
- `DecisionScoreService`
- `RealestateDecisionService`
- `DecisionCandidate`
- `DecisionResult`
- 최근 거래, 평균가, 평당가, 거래건수, 면적 적합도, 예산 적합도 기반 점수화

### 9. 비교 답변 고도화

비교 질문에서 후보가 한쪽 지역으로 치우치거나, 단지명/지역명을 잘못 구분하는 문제가 있었다.

개선 내용:

- `대치동 vs 역삼동` 같은 다중 지역 비교 분리
- `잠실엘스랑 대치동 비교` 같은 단지명/지역명 혼합 비교 처리
- 비교 대상별 후보 균형 조정
- 대상별 요약 테이블 추가
- 평균가, 중위가, 최근가, 최저/최고, 평당가, 거래건수 제공

### 10. 답변 히스토리 저장

최근 질문 클릭 시 다시 요청하는 방식은 사용자 입장에서 히스토리로 보기 어렵다. 그래서 질문 이벤트에 당시 답변 스냅샷을 저장하도록 확장했다.

추가 저장 항목:

- `query`
- `answer`
- `sources`
- `decision`
- `model`
- `createdAt`

관련 migration:

- `V15__add_user_ai_memory_answer_snapshot.sql`

### 11. 지역 필터 정밀화

`마포` 검색이 `마포구`뿐 아니라 `마포리`까지 잡는 문제가 있었다. 이는 법정동 이름을 `%마포%`로 검색하던 fallback 때문에 발생했다.

개선 내용:

- 시군구 코드 테이블을 먼저 조회
- `마포` → `마포구` → `11440`으로 고정
- 시군구가 매칭되면 법정동 fallback을 타지 않음
- RAG 검색 SQL과 의사결정 후보 SQL 모두 동일하게 수정

## 남은 개선 포인트

1. 지역 resolver를 별도 컴포넌트로 분리
   - 현재는 SQL과 query rewrite 쪽에 지역 해석 로직이 나뉘어 있다.
   - 장기적으로 `RegionResolver`를 두고 시군구/법정동/행정동 해석을 한 곳에서 관리하는 편이 좋다.

2. 단지명 resolver 추가
   - 지역명과 단지명이 섞인 질문에서 더 안정적인 판별이 필요하다.
   - 예: `잠실엘스랑 대치동 비교`

3. 히스토리 상세 API 분리 검토
   - 현재 최근 이벤트 목록에 답변 스냅샷까지 내려준다.
   - 히스토리가 커지면 목록 API와 상세 API를 분리하는 편이 낫다.

4. 의사결정 점수 설명 강화
   - 점수 자체는 제공되지만, 사용자가 왜 그 점수가 나왔는지 더 명확히 볼 수 있어야 한다.
   - 예산/면적/거래량/최근성 breakdown UI를 더 강화할 수 있다.

5. RAG와 deterministic 분석의 역할 분리
   - 가격/거래량/비교는 DB 집계가 우선이다.
   - 설명/요약/문장화는 LLM이 맡는 구조로 더 명확히 분리하는 것이 좋다.
