## 1. 경험 소개

---

**Q. RAG나 LLM을 사용한 경험을 설명해주세요.**

부동산 실거래 데이터를 기반으로 사용자의 자연어 질문에 답하는 RAG 기능을 구현했습니다.
PostgreSQL의 실거래 데이터를 검색용 텍스트 문서로 가공하고,
OpenAI 또는 로컬 Ollama 임베딩 모델로 벡터를 생성해 pgvector에 저장했습니다.

질문이 들어오면 같은 임베딩 모델로 질문 벡터를 만들고 cosine distance가 가까운 문서를 검색합니다.
지역, 가격, 면적, 거래 시점처럼 구조화된 조건은 메타데이터 필터로 함께 적용하고,
검색된 실거래 문서를 근거로 LLM이 답변하도록 구성했습니다.

또한 문서 내용이 변경된 경우에만 다시 임베딩하도록 content hash를 사용했고,
대량 임베딩 작업은 Outbox와 Kafka를 이용해 비동기로 처리할 수 있게 설계했습니다.

---

**Q. 프로젝트에서 본인이 직접 담당한 부분은 무엇인가요?**

실거래 데이터를 RAG 문서로 변환하는 로직, 임베딩 모델 추상화,
pgvector 저장과 유사도 검색, 검색 결과를 LLM 프롬프트로 구성하는 흐름을 구현했습니다.

OpenAI와 Ollama를 동일한 인터페이스로 사용할 수 있게 분리했고,
근거 문서가 없을 때 LLM을 호출하지 않는 처리와 답변 출처 반환도 구현했습니다.
LLM 자체를 학습하거나 모델 서버를 대규모로 운영한 경험보다는,
기존 모델을 활용해 도메인 RAG 애플리케이션을 설계하고 연결한 경험에 가깝습니다.

## 2. RAG 기본 개념

---

**Q. RAG가 무엇인가요?**

RAG는 Retrieval-Augmented Generation, 즉 검색 증강 생성입니다.
LLM이 학습 당시의 지식만으로 답변하지 않고,
질문과 관련된 외부 문서를 먼저 검색한 뒤 그 문서를 근거로 답변하게 하는 방식입니다.

전체 과정은 문서 수집과 가공, 임베딩 생성, 벡터 저장,
질문 임베딩, 관련 문서 검색, 프롬프트 구성, LLM 답변 생성으로 나눌 수 있습니다.
최신 데이터나 사내 문서처럼 모델이 원래 알지 못하는 정보를 답변에 활용할 수 있다는 장점이 있습니다.

---

**Q. RAG를 사용하면 환각이 없어지나요?**

없어지지는 않습니다.
관련 문서를 검색하지 못하거나, 잘못된 문서를 검색하거나,
LLM이 제공된 문맥 밖의 내용을 추론하면 여전히 환각이 발생할 수 있습니다.

그래서 검색 품질을 먼저 확보하고, 프롬프트에 제공된 근거 안에서만 답변하도록 지시해야 합니다.
저는 검색 결과가 없으면 LLM을 호출하지 않고 안내 메시지를 반환하고,
답변과 함께 사용한 실거래 문서의 출처와 유사도를 제공하는 방식으로 위험을 줄였습니다.

---

**Q. RAG와 파인튜닝은 어떻게 다른가요?**

RAG는 실행 시점에 외부 문서를 검색해 모델에 전달하고,
파인튜닝은 학습을 통해 모델의 가중치를 변경합니다.

자주 변경되는 실거래 데이터나 사내 문서는 RAG가 적합합니다.
답변 말투, 출력 형식 또는 반복적인 업무 패턴을 모델에 학습시키려면 파인튜닝을 검토할 수 있습니다.
두 방식은 대체 관계라기보다 필요에 따라 함께 사용할 수 있습니다.

---

## 3. 문서와 임베딩 파이프라인

---

**Q. 원본 데이터를 어떻게 RAG 문서로 만들었나요?**

DB 레코드를 그대로 임베딩하지 않고 지역, 아파트명, 거래금액,
면적, 층, 거래일처럼 검색에 필요한 정보를 일관된 텍스트 형식으로 구성했습니다.
동시에 원본 ID와 지역·가격·날짜 같은 값을 메타데이터로 별도 저장했습니다.

텍스트는 의미 유사도 검색에 사용하고 메타데이터는 정확한 필터에 사용합니다.
예를 들어 "강남구 10억 이하 아파트"라는 질문이라면
의미 검색에만 의존하지 않고 지역과 가격 조건을 SQL 필터로 적용할 수 있습니다.

---

**Q. 문서를 어떻게 chunking했나요?**

현재 프로젝트의 실거래 한 건은 내용이 짧고 구조가 단순해서
거래 한 건을 하나의 문서 단위로 사용했습니다.
긴 문서를 일정 글자 수로 나누는 일반적인 chunking 문제는 크지 않았습니다.

특허 명세서처럼 긴 문서를 처리한다면 제목, 초록, 청구항, 상세 설명을 먼저 구분하고,
문단이나 청구항처럼 의미가 유지되는 단위로 나누겠습니다.
Chunk가 너무 작으면 문맥이 끊기고 너무 크면 관련 없는 내용과 토큰 비용이 증가하므로
실제 질문 평가셋으로 검색 품질과 비용을 비교해야 합니다.

---

**Q. Embedding이 무엇이고 어떤 기준으로 모델을 선택했나요?**

Embedding은 텍스트의 의미를 숫자 벡터로 표현하는 방식입니다.
의미가 비슷한 텍스트는 벡터 공간에서도 가까운 위치에 놓이도록 학습됩니다.

프로젝트에서는 OpenAI 임베딩과 로컬 Ollama 임베딩을 모두 사용할 수 있게 했습니다.
모델을 선택할 때는 한국어 검색 품질, 벡터 차원, 호출 비용,
응답시간, 데이터 외부 전송 가능 여부를 함께 고려합니다.
모델별 벡터 공간은 호환되지 않기 때문에 저장할 때 provider와 model 정보를 함께 관리했습니다.

---

**Q. 변경되지 않은 문서도 매번 임베딩하나요?**

아닙니다. 문서 내용으로 content hash를 만들고 기존 hash와 비교합니다.
내용이 같으면 기존 문서와 임베딩을 유지하고, 변경된 문서만 다시 임베딩합니다.

임베딩 API 비용과 처리 시간을 줄일 수 있고,
주기적으로 원본 데이터를 동기화해도 불필요한 작업을 피할 수 있습니다.
모델 자체를 교체한 경우에는 내용이 같더라도 새 모델로 전체 재임베딩해야 합니다.

## 4. 검색 설계

---

**Q. 왜 Elasticsearch가 아니라 pgvector를 사용했나요?**

프로젝트가 이미 PostgreSQL을 사용하고 있고 초기 데이터 규모가 크지 않아
별도 검색 인프라를 추가하지 않고 pgvector로 시작하는 것이 적절했습니다.

벡터 유사도 검색과 지역, 가격, 면적 같은 SQL 조건을 한 쿼리에서 처리할 수 있고,
원본 데이터와 벡터 데이터의 일관성을 관리하기도 단순했습니다.
데이터와 검색 트래픽이 크게 증가하거나 BM25와 벡터 검색의 결합이 중요해지면
Elasticsearch 또는 OpenSearch의 hybrid search도 검토할 수 있습니다.

---

**Q. pgvector 검색은 어떻게 구현했나요?**

문서 임베딩에 HNSW 인덱스를 구성하고 cosine distance 연산자를 사용했습니다.
질문 벡터와 문서 벡터의 거리를 계산해 가까운 문서를 topK만큼 조회합니다.

실거래 검색에서는 벡터 유사도만 보지 않고 지역, 가격, 면적과 같은 조건을 먼저 적용합니다.
필요한 경우 유사도에 최신성 점수를 일부 결합해 최근 거래가 너무 아래로 밀리지 않도록 했습니다.

---

**Q. topK는 어떻게 정하나요?**

topK가 너무 작으면 필요한 근거를 놓치고,
너무 크면 관련 없는 문서가 프롬프트에 포함되어 답변 품질과 응답시간이 나빠집니다.
LLM 입력 토큰과 비용도 증가합니다.

현재 API에서는 과도한 요청을 막기 위해 topK 상한을 두었습니다.
실무적으로는 대표 질문과 기대 문서로 평가셋을 만들고
Recall@K, 답변 정확도, 지연시간과 토큰 비용을 비교해 결정해야 합니다.

---

**Q. Vector Search와 키워드 검색은 언제 각각 사용하나요?**

Vector Search는 표현이 달라도 의미가 비슷한 문서를 찾는 데 유리합니다.
반면 아파트명, 지역 코드, 특허번호처럼 정확한 단어가 중요한 검색은 키워드 검색이 더 적합합니다.

가격과 날짜 범위는 벡터 유사도에 맡기지 않고 구조화된 필터로 처리해야 합니다.
두 방식이 모두 필요한 경우 BM25와 vector search 결과를 RRF 같은 방식으로 결합하는
hybrid search를 사용할 수 있습니다.

---

## 5. LLM 답변 생성

---

**Q. 검색 결과를 LLM에 어떻게 전달했나요?**

검색 결과를 번호가 있는 근거 목록으로 정리하고,
지역, 아파트명, 거래금액, 면적, 거래일과 유사도를 프롬프트에 포함했습니다.
LLM에는 제공된 자료를 기준으로 답하고 근거가 없으면 추측하지 않도록 지시했습니다.

답변 API는 최종 텍스트뿐 아니라 실제로 사용한 source 목록도 함께 반환합니다.
사용자가 답변의 근거를 확인할 수 있고 운영 중 잘못된 답변을 분석하기도 쉬워집니다.

---

**Q. OpenAI와 Ollama를 모두 지원한 이유는 무엇인가요?**

OpenAI는 품질과 사용 편의성이 좋지만 호출 비용과 외부 네트워크 의존성이 있습니다.
Ollama는 로컬에서 실행할 수 있어 데이터 외부 전송을 줄이고 반복 개발 비용을 낮출 수 있습니다.

두 구현체가 공통 인터페이스를 따르도록 만들어 서비스 코드가 특정 제공자에 직접 의존하지 않게 했습니다.
다만 모델별 품질과 임베딩 차원이 다르기 때문에 설정만 바꾸면 무조건 동일하게 동작한다고 보지는 않고,
모델별 평가와 별도 임베딩 관리가 필요합니다.

---

## 6. 운영과 개선

---

**Q. 대량 임베딩 작업은 어떻게 처리했나요?**

작은 작업은 동기 배치로 처리할 수 있지만,
대량 작업이 API 요청과 같은 트랜잭션에서 실행되면 timeout과 장애 전파 위험이 있습니다.

그래서 임베딩 요청을 Outbox에 저장하고 Kafka consumer가 비동기로 처리하는 흐름을 구성했습니다.
실패 작업은 재시도 횟수와 상태를 기록하고 반복 실패는 DLQ로 분리할 수 있게 했습니다.
핵심은 메시지가 중복 전달되더라도 문서 키와 모델 정보를 기준으로 멱등하게 처리하는 것입니다.

---

**Q. RAG 시스템에서 어떤 지표를 확인해야 하나요?**

검색 단계에서는 Recall@K, 유사도 분포, 검색 결과 없음 비율을 확인합니다.
생성 단계에서는 답변 정확성, 제공 근거와 답변의 일치 여부,
출처 정확성과 근거가 없을 때 적절히 답변을 거부하는지를 봅니다.

운영 지표로는 임베딩과 검색, LLM 호출의 단계별 지연시간,
API 오류율, 토큰 사용량, 비용, Kafka lag와 재시도 건수를 확인해야 합니다.
현재 프로젝트에서는 구조와 테스트를 구현한 수준이고,
실제 대규모 트래픽 기반의 장기 A/B 테스트 경험은 없다고 구분해서 답하겠습니다.

---

**Q. 현재 구현에서 개선하고 싶은 부분은 무엇인가요?**

첫째, 실제 사용자 질문과 정답 문서로 구성된 평가셋을 확대하고 싶습니다.
현재 파라미터가 합리적인지 판단하려면 정량적인 검색 품질 측정이 필요합니다.

둘째, 정확한 아파트명 검색과 의미 검색을 결합한 hybrid retrieval을 검토할 수 있습니다.
셋째, 검색 후보를 넓게 가져온 뒤 reranker로 순서를 다시 정하면
LLM에 전달되는 근거의 품질을 높일 수 있습니다.

다만 기능을 한꺼번에 추가하기보다 검색 실패 사례를 수집하고,
가설별로 Recall, 답변 품질, 지연시간과 비용을 비교하면서 적용하겠습니다.
